GitHub repo explorer & repo map

AnvilCV now reads your code itself, private repos included, and builds resume bullets from what it actually finds. That replaces copying a prompt into a coding agent and pasting its output back.

TL;DR
  • Connect GitHub (read-only, repos you pick) and import a repo as a project pinned to a commit.
  • AnvilCV downloads the repo once and builds a repo map: modules ranked by importance, numbers counted from the code, and summaries from modules up to the whole project.
  • An explorer uses the map to read the right files and fills project context. Anything it can't back with code is dropped.
  • Bullets are written from stories: one call picks the strongest work with quotes checked against the source, a second writes one or two wordings per story and lens. Every bullet links to the files or commits it came from.
  • Bullet rules follow recruiter research: mostly one line, one bold on those, and a measured result only when the source states one. Activity counts (commits, lines, tests) are cut.
  • The old Copy for LLM button and the agent download are gone. Manual paste still works.

The flow

What each stage does

1 · Connect

GitHub App with contents:read + metadata:read only. The callback checks a one-time session state and links an installation only if the user's own OAuth token lists it. Only the installation id is stored.

2 · Import

Import from GitHub lists the repos you granted. The project is pinned to the branch head commit, so the tree, files, map, and evidence all describe the same snapshot.

3 · Snapshot

One tarball request instead of one API call per file. Vendored, lockfile, binary, and oversized files are skipped. Caps: 100 MB download, 25 MB of text.

4 · Repo map (no LLM)

Aider-style skeleton: public symbols and routes per file (regex, per language), module links from cross-module references, and PageRank so the code everything depends on ranks first. Also counts tests, endpoints, migrations, dependencies, lines of code, and CI.

5 · Summaries

Bottom-up, like CodeWiki / RepoAgent. The top 15 modules get what / how / why. Then the project gets an overview, its audience, 3-7 subsystems tagged with the lenses they feed, and 2-3 end-to-end flows. Cached per commit.

6 · Explorer

LLM tool loop (read_file, git_log, search_code, list_tree) that sees the map first. Budgets on steps, files, tokens, and time. Ported from anvilcv-context-mcp's instructions.

7 · Verify

Citations to files it never read are dropped. Evidence text is re-sliced from the real file. Any sentence whose number appears nowhere in the code is cut. Blank fields keep what the user typed.

8 · Generate

One call picks the strongest work from the overview and the requested lenses' subsystems; quotes not found in the source are dropped. Each new story then gets a slot on its best lens: 15 candidate wordings from four angles (outcome, decision, scale, failure), code filters, dedup, a code score, and a recruiter judge run twice. One or two wordings are kept. Code cuts vanity counts, filler, invented numbers, and bad lengths. Approved bullets are never touched.

9 · Triage

The Repo tab puts the file tree and map beside the bank. Each bullet shows its sources; click one to open the cited lines. Approve or reject inline.

Why bullets should get better

  • Before: every lens rewrote the same ~10 text fields, so bullets overlapped and stayed generic.
  • After: the map gives concrete what / how / why per module, and the story pass picks distinct pieces of work first, so a lens the project barely touches gets no bullets instead of padding.
  • The Y problem: code rarely states outcomes. The Y is written only when the source states a result; activity counts ("352 test cases", "47 endpoints") are real but impress nobody, so the filters cut them.

Changes by layer

Backend (com.resumepipeline.github)

  • GithubAppAuth: app JWT from the private key (PKCS#1 or PKCS#8). GithubClient: installation tokens, repos, tree, files, search, commits, tarball.
  • RepoSnapshot, RepoMapBuilder, RepoMapService, and RepoMapRenderer build the repo map. RepoExplorer runs the tool loop. SourceTracer links bullets to their sources.
  • LlmClient gains exploreStep, summarizeModule, and summarizeProject. GenerateBulletsRequest gains lensFocus.

Data

  • V30: github_installation (user → installation id, no tokens), plus project.repo_branch, repo_commit_sha, repo_evidence.
  • V31: project.repo_map (JSON, reused until the pinned commit changes).

Frontend

  • Settings: GitHub connection panel. Projects: Import from GitHub.
  • Project and experience pages: Bullets, Generate (story, lens, generate) and Repo tabs. The Repo tab has the file tree and viewer, the repo map and the explorer. Experiences show a warning and need an acknowledgement before the explorer runs. The bank is on the Bullets tab; the bullet source links are no longer shown in the UI.

Setup

Create a GitHub App (steps in the README under GitHub App). Set GITHUB_APP_ID, _SLUG, _CLIENT_ID, _CLIENT_SECRET, and _PRIVATE_KEY. With them unset the feature is off and nothing else changes. Migrations run on startup.

Costs & limits

  • The first explore on a commit makes about 16 map calls, then up to 40 explorer steps. Later runs reuse the map. Usage is logged as repo_explore.
  • Symbol extraction is regex-based. It is strong for Java, TS/JS, Python, and Go, and loose elsewhere. A missed symbol only weakens ranking and never adds a claim.
  • Pending bullets still feed tailoring (existing behavior). Bare counts without a unit (e.g. "10,000 users") are not number-checked.
  • Not yet run end-to-end against a live GitHub App.
